# Redis 캐싱 + k6 + Prometheus + Grafana 실행 가이드

## 전체 그림

```
[k6] --부하--> [스프링부트 :8080] --캐시--> [Redis :6379]
                    |
                    | /actuator/prometheus (메트릭 노출)
                    v
             [Prometheus :9090] --수집한 데이터--> [Grafana :3000] (그래프로 시각화)
```

- **Redis**: 자주 조회하는 상품 목록을 메모리에 저장해서 DB 조회를 건너뜀
- **k6**: 가상 사용자 수십 명이 동시에 API를 호출하는 상황을 시뮬레이션
- **Prometheus**: 앱의 상태(요청 수, 응답 시간, JVM 메모리 등)를 5초마다 수집
- **Grafana**: Prometheus가 모은 숫자를 그래프 대시보드로 보여줌

---

## 0. 사전 설치 (한 번만)

1. **Docker Desktop** — https://www.docker.com/products/docker-desktop/ 설치 후 실행
2. **k6** — 관리자 PowerShell에서:
   ```
   winget install k6 --source winget
   ```

## 1. 인프라 켜기 (Redis + Prometheus + Grafana)

backend 폴더에서:

```
docker compose up -d
```

확인: `docker ps` 하면 vegan-redis, vegan-prometheus, vegan-grafana 3개가 떠 있어야 함.

## 2. 스프링부트 앱 실행

평소처럼 IDE에서 실행 (MySQL도 켜져 있어야 함).
새 의존성 때문에 처음엔 Gradle 새로고침이 필요할 수 있음.

확인 3가지:

- http://localhost:8080/actuator/health → `"status":"UP"` 이면 정상
- http://localhost:8080/actuator/prometheus → 메트릭 텍스트가 잔뜩 보이면 정상
- 상품 목록 API를 2번 연속 호출 → 콘솔에서 SQL이 **첫 번째만 찍히면** 캐시 작동 중

Redis 내용 직접 보기:

```
docker exec -it vegan-redis redis-cli
> KEYS *              # products::all 같은 키가 보임
> TTL "products::all" # 남은 유효시간(초)
```

## 3. Prometheus 확인

http://localhost:9090 접속 → Status > Targets 메뉴 → `vegan-api`가 **UP**이면 수집 중.

검색창에 쿼리를 넣어볼 수 있음:

```
http_server_requests_seconds_count        # 엔드포인트별 누적 요청 수
rate(http_server_requests_seconds_count[1m])  # 초당 요청 수(RPS)
jvm_memory_used_bytes                     # JVM 메모리 사용량
```

## 4. Grafana 대시보드

1. http://localhost:3000 접속 (admin / admin)
2. 왼쪽 메뉴 Connections > Data sources > Add data source > **Prometheus** 선택
   - URL: `http://prometheus:9090` (컨테이너끼리는 서비스 이름으로 통신)
   - Save & test
3. Dashboards > New > **Import** > ID에 **4701** 입력 (JVM Micrometer 공식 대시보드)
   - 데이터소스로 방금 만든 Prometheus 선택
4. 완료 — JVM 메모리, GC, 스레드, 요청 통계가 실시간 그래프로 보임

Spring Boot 전용 대시보드는 ID **11378** (Spring Boot Statistics)도 인기 있음.

## 5. k6 부하 테스트

backend 폴더에서:

```
k6 run k6/load-test.js
```

약 2분 30초 동안 가상 사용자가 최대 50명까지 늘면서 상품 API를 두드림.
**돌리는 동안 Grafana를 열어두면** 요청 수/응답 시간이 실시간으로 치솟는 게 보임.

끝나면 요약이 출력됨. 주요 지표:

- `http_req_duration` 의 `p(95)` — 요청의 95%가 이 시간 안에 처리됨 (500ms 기준 통과 여부)
- `http_req_failed` — 실패율
- `iterations` — 시나리오 총 실행 횟수

## 6. 캐시 효과 비교 실험 (추천!)

1. 지금 상태(캐시 ON)로 `k6 run k6/load-test.js` → p(95) 기록
2. application.properties에 `spring.cache.type=none` 추가하고 앱 재시작 (캐시 OFF)
3. 다시 k6 실행 → p(95) 비교
4. 실험 끝나면 `spring.cache.type=redis`로 복구

상품 데이터가 많을수록 차이가 극적으로 벌어짐. 상품이 몇십 개면 차이가 작을 수 있는데,
그 자체도 "캐시는 병목이 있을 때 의미가 있다"는 좋은 교훈.

## 캐시 동작 원리 (공부 포인트)

```java
@Cacheable(value = "products", key = "'all'")
public List<Product> getAll() { ... }
```

1. 호출되면 먼저 Redis에서 `products::all` 키를 찾음
2. **있으면** DB에 안 가고 캐시 값을 바로 반환 (캐시 히트)
3. **없으면** 메서드를 실행(DB 조회)하고 결과를 Redis에 저장 (캐시 미스)
4. 60초(TTL) 지나면 자동 삭제 → 다음 호출이 다시 DB에서 최신 데이터를 가져옴
5. 상품 추가/수정/삭제/주문 시 `@CacheEvict(allEntries = true)`가 캐시를 즉시 비움
   → 사용자가 옛날 데이터를 보는 시간 최소화
